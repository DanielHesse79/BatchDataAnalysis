# Batch Insight Analyzer

Batch Insight Analyzer is a local Streamlit application for linking batch process
parameters to QC outcomes. It is designed for bioprocess and life-science
manufacturing teams that have historical batch data, but may not have a
statistician or data scientist available.

The app lets a user upload a batch process file and a QC results file, match the
files by batch ID, profile the merged data, run several complementary analysis
methods, and generate a plain-language interpretation through Ollama.

## Current Status

This repository contains the working foundation through local interpretation:

- Synthetic validation data generator.
- CSV, XLSX, and XLS upload.
- Batch ID matching and inner join.
- Data profiling and pre-flight audit checks.
- QC trend and control-chart views.
- Field-data intake controls for sheet/header selection, numeric text parsing,
  batch ID normalization, duplicate handling, long-format pivoting, readiness
  scoring, and mapping profile export.
- Built-in data templates, including a combined Excel workbook template for
  process and QC data on separate sheets.
- Optional spec/window upload and historical margin assessment.
- PCA for exploratory batch structure.
- PLS regression with VIP-style variable ranking.
- Random Forest regression with permutation importance.
- Combined ranked driver table across methods.
- Suggested historical response bands for numeric drivers, so middle-band sweet
  spots are not mistaken for simple higher/lower trends.
- Deterministic evidence/report-pack layer before LLM interpretation.
- Heuristic report validation for likely hallucinations or overclaims.
- Local or Ollama Cloud interpretation.
- PDF report export with summary tables, driver charts, PCA overview, specs, and appendix.
- Streamlit UI polish and theme.

## What The App Is For

Use Batch Insight Analyzer to answer questions like:

- Which process variables are most associated with yield?
- Which raw material lots, bioreactors, or shifts look different?
- Are there non-linear quality risks, such as high temperature plus long
  duration?
- Do PCA, PLS, and Random Forest agree on the same drivers?
- Are process windows or QC specs potentially too narrow, too wide, or poorly
  explored by historical data?
- What data quality issues should be reviewed before trusting the results?

The app is for process understanding and investigation support. It is not a
validated batch-release system and should not be used as the sole basis for GMP
release decisions.

## Quick Start

From the project root:

```powershell
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
python generate_synthetic_data.py
streamlit run app.py
```

Then open:

```text
http://localhost:8501
```

If Streamlit is already installed in the local virtual environment, this also
works:

```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py --server.port 8501
```

Run the automated tests:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

The test suite covers intake helpers, profiling/audit checks, specs/windows,
deterministic evidence, confidence explanations, report validation, and recovery
of the planted synthetic relationships.

## Ollama Setup

The interpretation tab uses Ollama's chat API.

Default local Ollama URL:

```text
http://localhost:11434
```

Recommended local models for this app:

- `ministral-3:14b` for a good speed/quality balance.
- `qwen3.5:9b` for quick iteration.
- `mistral-small3.2:24b` for slower but more polished reports.

The app also includes `nemotron-3-super:cloud` as a selectable shortcut. Cloud
models may route the analysis summary through Ollama Cloud, so only use them for
data you are comfortable sending outside the machine.

Optional `.env` values:

```text
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=ministral-3:14b
```

## Optional CatBoost Explainability

The main analysis uses PCA, PLS, and Random Forest. An optional CatBoost + native
SHAP tab is available for deeper non-linear/categorical explanation when
CatBoost is installed:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-optional.txt
```

This optional model does not currently change the main ranked-driver score. Use
it as a comparison layer when lot, supplier, reactor, operator, or other
categorical effects may matter.

## Synthetic Validation Data

The repository includes synthetic data in `data/`, generated by
`generate_synthetic_data.py`.

The known planted relationships are:

- `yield_g_L` is strongly positive with `feed_rate_day3_mL_h` and
  `temperature_C`.
- `purity_percent` drops when `raw_material_lot_supplier == "Supplier_B"`.
- `aggregate_percent` has a U-shaped relationship with `ph_setpoint`, with a
  minimum around pH 7.0.
- `hcp_ppm` spikes when high temperature and long duration occur together.
- `bioreactor_id == "BR-3"` has lower yield.

The repository also includes `data/synthetic_specs.csv`, which can be uploaded
as an optional spec/window file to test margin assessment.

For a more production-style spec test, use:

- `data/mock_spec_process.csv`
- `data/mock_spec_qc.csv`
- `data/mock_spec_specs.csv`

Those files include sodium hydroxide process-window examples, a moisture QC
limit, residual NaOH, drying behavior, target-shift behavior, and intentionally
challenging spec/window cases.

For a messy field-data intake test, run:

```powershell
python generate_messy_field_data.py
```

Then upload:

- `data/messy_process_export.xlsx`
- `data/messy_qc_long.csv`

Those files include title rows before headers, decimal commas, values with
units, `<` qualifiers, duplicate batch rows, inconsistent batch IDs, and
long-format QC results.

These relationships are intentional. They give the app a reality check: if the
analysis does not recover these signals, the workflow needs attention.

## Key Limitations

- Findings are associative, not causal.
- Historical batch data can be confounded by time, campaign, operator, lot, or
  equipment changes.
- Quartile thresholds and interaction screens are exploratory, not optimized
  setpoints.
- Suggested response bands are historical sweet-spot hypotheses, not validated
  design spaces.
- Spec/window assessments are historical checks, not proof of a design space.
- Driver confidence labels are practical explanations, not formal statistical
  validation.
- Random Forest and PLS can overfit small datasets if validation is weak.
- Messy intake normalization improves matching and parsing, but it does not
  replace domain review of source data.
- LLM interpretations can be useful, but the numerical results and audit
  warnings remain the source of truth. The UI now shows Python-generated key
  findings and confidence breakdowns before the LLM narrative.
